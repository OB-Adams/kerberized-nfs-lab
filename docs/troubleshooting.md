# Troubleshooting log

Real failures hit while building this lab, with the diagnosis path for each.

| Symptom | Diagnosis | Cause / fix |
|---|---|---|
| Lab names resolve but external names return SERVFAIL; chronyd on ldap cannot resolve its NTP servers | `dig +cd` through BIND gives NOERROR; the named log shows `broken trust chain resolving 'org/DS/IN'`, first via the router and then via 1.1.1.1; `dig @1.1.1.1 +dnssec` returns no RRSIG; `dig @1.1.1.1 id.server CH TXT` times out | The upstream network intercepts port 53 and answers with a forwarder that strips DNSSEC data, so validation fails at the first DS record whatever forwarder is set. Set `dnssec-validation no` as a documented trade-off (production: encrypted DNS, DoT/DoH). Side effect fixed: chronyd on ldap resolved its time servers again and moved from stratum 10 (local clock) to an internet source. |
| SSSD on client stays `Offline`; `id kofi` says no such user | `sssctl debug-level 6`; `sssd_lab.local.log` shows `Password Policy Response: ... error [Account locked]` and `Bind result: Constraint violation(19), Exceed password retry limit` for sssd-bind (the "Failed to resolve server ... no data" lines after it were AAAA lookups during failover, not the cause) | A wrong password in `sssd.conf` made SSSD fail three binds, so the global lockout policy locked the service account; while locked even the correct password is refused. Design flaw: anyone could lock sssd-bind and take every client offline. Fix: subtree password policy on `ou=Services` with lockout off (`nsslapd-pwpolicy-local=on`, `dsconf lab localpwp addsubtree ou=Services,dc=lab,dc=local --pwdlockout off`), a 32-character random password for sssd-bind, and `lookup_family_order = ipv4_only` in sssd.conf. |
| M5 restore-drill logs from ldap and client put events in an impossible order (client loses a user before ldap deletes it, finds her again before ldap restores her) | Laying the two `run()` logs side by side: every client event sits about 16-18 s before the ldap event that caused it, consistently across two runs | Client's clock was ~18 s behind. The VMs pause while the host Mac sleeps, and the default `makestep 1.0 3` only allows chrony to step the clock during its first 3 updates; after that it only slews. Set `makestep 1.0 -1` on every host (step whenever the offset exceeds 1 s). After the change both logs line up to the second. Matters for Kerberos, which rejects requests more than 5 minutes off. Seen again in K3 on a larger scale: after the Mac slept ~3 h, ldap's `chronyc sources` showed the only server as `^~` (too variable) with Reach 1 and an offset of -11110 s, so no source was selectable and `makestep` could not act; `chronyc burst 4/4` then `chronyc makestep` corrected it, followed by the same on client and fresh tickets. |
| Kerberos lockout never triggers: after 5 wrong `kinit`s `getprinc` still shows `Failed password attempts: 0` and `Last successful authentication: [never]`, even for principals that got tickets | 389-ds access log: every MOD from the KDC's connection (bound as kdc-service) on user and container principals returns `err=50`; a manual `ldapmodify` of `krbLastFailedAuth` as kdc-service succeeds. ACL tracing (`nsslapd-errorlog-level=128`) names the refused attribute, one per run: first `Deny write ... attr(krbExtraData) to uid=kdc-service`, then, after an admin unlock, `attr(krbLastAdminUnlock)` | The KDC writes `krbExtraData`, and after `modprinc -unlock` also `krbLastAdminUnlock`, in the same modify as the login bookkeeping attributes. An LDAP modify is all-or-nothing, so a missing right on one attribute discarded the whole update. Added both to the kdc-service write ACIs (`ou=People` and `cn=krbcontainer`). Lockout and last-login tracking then work. |
| `kinit` from client fails at once with `Cannot contact any KDC for realm 'LAB.LOCAL'`, although the SRV lookup in the trace returns `ldap.lab.local` port 88 | `systemctl is-active krb5kdc kadmin` on ldap: both inactive, so nothing was listening on port 88 (a closed port and a firewall block give the same client error) | With the kldap backend the KDC and kadmind need 389-ds to read their database, but their units only order after the network, so nothing guaranteed the directory was up first. Added drop-ins `configs/systemd/{krb5kdc,kadmin}.service.d/10-after-dirsrv.conf` (`After=` and `Requires=dirsrv@lab.service`). After a reboot both start on their own and `systemd-analyze critical-chain krb5kdc.service` shows the KDC waiting for `dirsrv@lab.service`. |
| SASL/GSSAPI bind as `host/client.lab.local` fails with `ldap_sasl_interactive_bind: Invalid credentials (49)`, while kofi's GSSAPI bind works; the errors log says `SASL(-14): authorization failure: security flags do not match required` | The access log shows the ticket round accepted (`err=14`, bind in progress) and only the final step refused, so Kerberos worked and authorization failed. The host entry and the mapping rule both existed. Trace logging (`nsslapd-errorlog-level=1` for one bind) showed `sasl_map_check - regex: host/(.*)@LAB\.LOCAL, id: host/client.lab.local, didn't match`, then the built-in `uid mapping` matching and building `(uid=host/client.lab.local)` | 389-ds receives the principal without the default realm, so a mapping regex that ends in `@LAB\.LOCAL` never matches; the next rule produced a filter no entry satisfies and the bind was refused. The "security flags" text was a stale SASL detail message, not the cause. Changed the regex to `^host/\(.*\)$` ([`ldif/sasl-map-hosts.ldif`](../ldif/sasl-map-hosts.ldif)); priority 10 keeps it ahead of `uid mapping`. The same realm stripping is why kofi maps through `uid mapping`, not `Kerberos uid mapping`. |

## LDAP result codes

Returned during this build, plus 32 and 65, which the M1 checks (backend suffix list, rfc2307compat schema) are there to prevent.

| Code | Name | Meaning here |
|---|---|---|
| 13 | Confidentiality required | password bind attempted without TLS: `Operation requires a secure connection` (`nsslapd-require-secure-binds=on`) |
| 19 | Constraint violation | account locked by password policy: `Exceed password retry limit. Please try later.` |
| 32 | No such object | base DN does not exist (or instance has no backend) |
| 48 | Inappropriate authentication | anonymous search outside the rootDSE: `Anonymous access is not allowed.` (`nsslapd-allow-anonymous-access=rootdse`) |
| 49 | Invalid credentials | wrong password or wrong bind DN |
| 53 | Unwilling to perform | bind with a DN but an empty password (unauthenticated bind); or bind as an administratively locked account: `Account inactivated. Contact system administrator.` (`dsidm ... account lock`, `nsAccountLock: true`) |
| 65 | Object class violation | entry breaks the schema (e.g. two structural classes) |
| 68 | Already exists | entry or config object (e.g. an index) already present |
